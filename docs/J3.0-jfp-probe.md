# J3.0 — Can DOS 4 VA use the ROM JFP?

**Yes from a DOS program; not a drop-in CON input backend. Recommend a project FEP.** On both vaeg VA and VA2, `ResJFP` → `KbFlsh` → `SetJFP` enabled real keyboard conversion without the screen editor. The ROM returned `日本` as two Shift-JIS words. But it took over the function-key label row, and with the labels hidden it overwrote DOS text. Its reset also opened DOS files. No product code changed.

Tested the 2HD distribution of MS-DOS `3280526578dd4ac405c30c7f90decd9a11a7e333` with vaeg `Rel.20261121 (m152, 20c8cba0)` on VA and VA2, using each model's ROMs and no saved config or backup RAM. Unless indicated otherwise, results below were observed on **both** models. The [gate](J3.0/gate.txt), [measurements](J3.0/observations.txt) and screens contain no ROM bytes or firmware target addresses.

## 1. Why is the callback null under DOS?

[`JFPBOOT.NAS`](../tests/pc88va/JFPBOOT.NAS) replaced only the boot sector on a disposable image. Before loading any DOS code it called `KyBook` (INT 82h AH=0Eh, returns ES:DX). On both models it found the documented RAM base (physical `00AB0h`), and returned `DI=4B42h`, `AX=0005h`: **KbAddr set, JFPAddr null, INT 8Dh vector set**. The four documented JFP data pointers were also null.

A separate cold boot of the untouched distribution sampled RAM at IO.SYS entry, the VAIO→SYSINIT transfer, the call into the relocated kernel, and the live COMMAND prompt. At all four stops JFPAddr was still null; KbAddr and the INT 8Dh vector compared byte-for-byte equal to their respective pre-DOS values. Thus on this native disk boot the ROM **hands off with the service installed but without the keyboard-side JFP link**. It isn't an initialized callback that VABOOT, VAIO, SYSINIT or DOS then clears. `ResJFP` installed the missing link under DOS (next section). Startup of the original PC-Engine or BASIC: **NOT RUN**; the handoff measurements don't establish what those environments initialize.

As a control, separately armed a breakpoint at `0000:0000` after entering the probe's unguarded `SnsChar` and `GetChar` modes. Both reached it before any test key. This reproduces the missing-link failure from [J0.1 §4](J0-probe.md#4-is-the-main-path-usable-and-why-did-v20-bypass-the-jfp) on the current build. The primitive queue control delivered all five test taps in order.

## 2. Initialization, ordinary/function keys, and the conversion key

The COM probe ran each sequence from a cold DOS prompt. It disabled ROM soft-key expansion (`ExpCtrl`, `AX=0201h`), sampled `GetJFP`, then polled `SnsChar` and paired each CF-clear result with a `GetChar`. Only the explicit negative controls bypassed the null-link guard.

| Sequence | Observation |
|---|---|
| `InitScr` + `AlcSysL` alone (`I`) | Callback and JFP pointers stayed null. |
| `IntKb` alone (`K`, INT 82h AH=05h) | Reached `0000:0000` from inside the call on both models. Starting with `K` also blocked the later stages in `KR`, `KRS`, and `KRJ`. |
| `SetJFP` alone (`S`, INT 8Dh CL=01h, `AX=0F00h DX=3C1Eh`) | VA2 returned `GetJFP=0F00/3C1E` but left the callback and pointers null. VA reached the call but not the immediate return instruction by frame 2500; the callback was still null in the bounded run. Not an initializer by itself on either model. |
| `ResJFP` alone (`R`, INT 8Dh CL=02h) | Returned with callback and all four documented data pointers set. `GetJFP` returned `AX=0080h DX=3C1Eh` (enabled, half-width alpha, direct input). One unsolicited sense/get pair appeared before test input. |
| `ResJFP` then `IntKb` (`RK`) or `KbFlsh` (`RF`, INT 82h AH=04h) | Both sequences returned with the link intact and no unsolicited pair at the pre-input checkpoint. `IntKb` need not be used. |
| `RF` then `SetJFP` (`RFJ`, `AX=0F03h DX=3C1Eh`) | Clean pre-input queue, `GetJFP=0F03/3C1E` (enabled, full-width kana, indirect; screen switch, dictionary edit and gaiji operations disabled). Successful keyboard conversion. |

In `R`, ignoring the pre-input sample, `a` returned `AX/BX=0061/1D61`, F1 returned `0000/6200` (scan retained, not an expanded string), and physical KANA held with `a` returned half-width `00C1/1DC1` (`ﾁ`). In `RFJ` the guest taps `N I H O N`, HENKAN, KETTEI produced `93FA/FFFF` then `967B/FFFF` (`日本`); nothing was delivered while the candidate was pending. `A`, KETTEI produced `82A0/FFFF` (`あ`). Every reported pair matched in sense and get. A direct `Sug1st` test (`RT`, INT 8Dh CL=04h) with synthetic `にほん` also produced `日本`, independently of the keyboard path. `Sug1st` without reset did not furnish a working path: VA did not reach the return checkpoint; VA2 returned without producing the requested candidate or installing the link.

**Physical keys:** With the `ResJFP` default, HENKAN alone in half-width mode delivered a space (`0020/3520`), not a mode switch. **ZENKAKU (全角)** changed the mode byte `80h→83h` on each model; an `a` then stayed pending until **KETTEI (決定)**. ZENKAKU while that character was pending did not switch modes, but after confirmation another ZENKAKU changed `83h→80h`, and `a` again came through as ASCII. HENKAN (変換) requests a candidate in full-width kana mode. `618JFP` §6.18.2 describes this distinction at the API level: control bit 6 permits/inhibits full-/half-width switching, mode bit 0 selects width, and control bit 7 separately disables JFP. The physical key names are in the `603KEYB` scan table. ZENKAKU did **not** toggle the master JFP enable bit in this test.

## 3. Display area and collisions

The [prompt captures](J3.0/va-prompt.png) ([VA2](J3.0/va2-prompt.png)) show the stock DOS 24+1 split. The probe sampled the same synthetic candidate under three layouts. The PNGs were rendered by vaeg from the corresponding paused states. TVRAM checks below refer to character-cell offsets, not firmware addresses.

| Layout and probe | Observed | VA / VA2 |
|---|---|---|
| Stock 24 text rows + labels (`RJ`) | On entering full-width kana, JFP replaced the J0.4 labels with its input row, including the mode indicator at right. The candidate appears at system buffer offset `0FA0h` (visible row 25); the DOS banner and main text outside that row stayed intact. After KETTEI the candidate cleared, but the labels did not return while still in full-width kana mode. | [VA](J3.0/va-rj-candidate.png) / [VA2](J3.0/va2-rj-candidate.png) |

Basic conversion used **one row, not a pop-up**. Returning to half-width with ZENKAKU restored the label cells in the `RZ` test, but left a mode indicator at the right. `617SCRNE` §6.17.2 reserves two system rows with `InitScr`, but reservation alone doesn't isolate the CON label row. A custom two-row split, longer candidate lists, and the dictionary/gaiji pop-up paths: **NOT RUN**.

## 4. RAM, dictionaries, and DOS reentrancy

The four far pointers from `618JFP` §6.18.6 were null at ROM handoff and at the DOS prompt. After `ResJFP` the active probes showed these **physical conventional-RAM locations**, stable through the measured conversion and key tests:

| Allocation | VA | VA2 |
|---|---:|---:|
| JFP bookkeeping | `04400h` | `04400h` |
| Conversion input buffer | `044A0h` | `044A2h` |
| Conversion output buffer | `0451Ch` | `0451Eh` |
| Status area | `0446Bh` | `0446Dh` |
| User dictionary environment | `04471h` | `04473h` |

The keyboard bookkeeping is at `00AB0h`. For comparison the boot-loaded IO.SYS and MSDOS.SYS occupy `[10000h,15400h)` and `[15400h,1EC00h)` (rounded to sectors); the kernel is then relocated to `112B:0000`. The DOS-owned first MCB in the prompt captures was at physical `1A660h`, with a valid chain through the top of the 640 KiB arena. The existing `MEMINFO` probe independently reported segment `1A66h` as the first MCB on both models. The measured work areas are below both the system files and the arena. This isn't a write-range proof for every JFP feature. The built-in dictionary is documented as ROM-backed (BNN manual, dictionary ROM description); `Decide` learning is documented as RAM-CG-backed (`618JFP` §6.18.3). The pointer above is a user-dictionary **environment**, not a measured buffer for a loaded user file. Successful user-file loading, learning persistence, and exhaustive RAM-write bounds: **NOT RUN**. Banked TVRAM is separate from this conventional RAM; the *screen writes* do overlap the label/main buffers as in §3.

**`ResJFP` calls DOS.** The probe temporarily chained INT 21h from the COM and counted two `AH=3Dh` file opens during `ResJFP`. Breakpoints in the probe's hook, while its phase was `R`, confirmed one `.DIC` and one `.DAT` pathname from conventional RAM on each model (opposite order). This matches the documented reset behavior of attempting to load a default user dictionary and a gaiji file. The distribution contained neither; there were no added opens during tested polling, conversion, confirmation or edit keys. The `HRJ` test separately logged its own `AH=40h` CON write.

**Do not make the reset/file path callable from inside a CON request.** `v4.0/src/DOS/DISP.ASM` increments `INDOS`, updates global saved-stack state and routes `AH=3Dh` to the disk stack; this isn't a general reentrant API. VAIO also has a single saved request stack (`ENTRY`, `SAVESP`/`SAVESS`). Even if ordinary keys in an already initialized JFP don't issue DOS calls in this test, that doesn't qualify arbitrary JFP paths for nested file I/O. An actual nested CON call, installed user-dictionary file, and dictionary modification via the ROM: **NOT RUN**.

## 5. Does it need the screen-editor BIOS?

**No for the measured conversion.** `RFJ` used VAIO's existing INT 83h setup, never called INT 94h, showed the candidate, and returned both kanji and the subsequent kana. `IRJ` used `InitScr`/`AlcSysL` and gave the same characters. `I` alone didn't set up the callback. The display ownership problem remains either way; `InitScr` isn't the missing keyboard initializer or a remedy for the label conflict.

## 6. DOS-facing byte shape and keys during composition

There is **one Shift-JIS word in AX per successful `GetChar`**, high byte first when serialized (`93 FA 96 7B` for `日本`), not one byte per ROM read. `BX=FFFFh` marks the generated characters in these tests. A byte-based CON adapter would need to queue the second byte and make status/peek/flush consistent with that queue. This ran at the BIOS boundary only: unchanged VAIO still reads the primitive queue. Prompt and EDLIN input through an integrated JFP, DOS break handling, and DOS Backspace across a committed pair: **NOT RUN** in this milestone.

`RJX` exercised pending hiragana on each model:

| Key while pending | Observation |
|---|---|
| Backspace | `A I BS KETTEI` returned only `82A0/FFFF` (`あ`). No BS was passed through while composing. |
| ESC | Cleared the composition, emitted nothing. Idle ESC produced `001B/001B`; forwarding that as an ordinary DOS byte would need a policy because J0.2 uses `1Bh` as a line-editor lead-in. |
| Ctrl-C | Cleared the composition and delivered `0003/FFFF`; when idle it delivered `0003/2B03`. These are BIOS returns, not observations of DOS processing Ctrl-C. |
| F1 / F6 | Neither delivered a DOS editing key while pending. F1 left pending `あ`; F6 changed the internal state and the next KETTEI committed `889F/FFFF` (`亜`). Idle F1 delivered `0000/6200` as above. Other F-keys while pending: **NOT RUN**. |

## Recommendation: project FEP

Keep the existing primitive CON input until a project FEP is ready. The ROM conversion engine is demonstrably functional; the recommendation is about **owning the console interaction**, not lack of a working init sequence or evidence of conventional-RAM overlap. A direct switch to the ROM main path would overwrite the chosen label/text layouts, change what reaches the DOS line editor during composition, and introduce a DOS file-call path that must be kept out of device requests. A different ROM integration could be investigated, but it hasn't been qualified here.

A project FEP needs composition/candidate UI that cooperates with both label modes, explicit key arbitration for DOS editing and break keys, and byte-accurate Shift-JIS delivery with consistent peek and flush. It also needs an owned memory budget and a conversion dictionary. The FreeDOS-88VA [M20 decision](https://github.com/FreeDOS-88VA/freedos/blob/66a6acef778ae6aebe5a9d85219788972d6eef9d/docs/porting/m20-report.md#decisions-carried-to-m21-japanese-support) is to use a project FEP that reads the installed machine ROM dictionary at run time, without distributing its contents. Check whether we can share that work; any user-file I/O should be kept out of nested CON requests.

## Reproduce

1. Build in scratch outside the repository as in [R1's `main` recipe](R1-boot-banner.md#reproduce): FreeDOS-88VA/freedos `7f467a2187a9e15c0c1bb84f179f214fe925153f`, emu2 `9d8698d06e67359bc8b230c2d19d5b1503e60819`, R1's distribution-builder patch, `msdos.branch=release/msdos-va` and `msdos.commit=3280526578dd4ac405c30c7f90decd9a11a7e333`. The builder used the pinned commit date (JST).
2. Run the NASM probes with the same emulator, using writable scratch disk copies. The runner defaults to both models and all cases, or takes case names after the output path. These destructive probe programs don't return to DOS; use a cold boot for each case. In particular, `B`, `G` and uninitialized `K` deliberately exercise broken paths.

   ```sh
   PYTHONPATH="$S/experiments/msdos4-va" python3 -B tests/pc88va/jfp-run.py \
     "$VAEG" "$ROMS" "$S/out/msdos4-pc88va-2hd.d88" "$S/runs"
   python3 -B tests/pc88va/jfp-observe.py "$S/runs"
   ```

3. For the candidate PNGs, from the corresponding `rj`, `hrj` or `irj` run directory, use a fresh vaeg instance of that model with the same disk. Use a debug script with `debug-script 1`, `limit-frame 2500`, `resource shot candidate.state`, `load-state shot`, `exit`, and `--screen-dump candidate.bmp`. The supplemental code checkpoints and build hashes are in [observations.txt](J3.0/observations.txt). Keep states, debug register captures, media and raw TVRAM private and outside the repository.

**Also NOT RUN:** physical hardware, VA3, 2D, reduced RAM selections, other MS-DOS builds/configurations, and original NEC OS/BASIC boot or input.
