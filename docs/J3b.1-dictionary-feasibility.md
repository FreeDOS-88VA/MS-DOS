# J3b.1 — ROM dictionary and headless JFP feasibility

**The dictionary is readable from DOS. An initialized JFP can also convert through its documented BIOS while its keyboard front end is disabled.** Use project-owned input and display for J3b.2; prototype the documented conversion backend in J3b.3 before committing to a ROM parser. This is a foreground feasibility result, not permission to call JFP from a DOS device request.

## 1. Access and banking

The PC-88VA Technical Manual (BNN, *MemMode* and §3.2.2) documents a V3 system-memory window at physical `A0000h–DFFFFh`. Read the **word** at port `0152h`. Change only `SMBC` (bits 11–8, low nibble of the high byte) to `Ch` for the documented 256 KiB dictionary window. The same selector chooses TVRAM (`1`, only the first 64 KiB), GVRAM (`4`), or kanji ROM #1/#2 (`8`/`9`; the latter selection also includes backup RAM). It is not the main ROM bank control. Preserve the ROM selectors and other mode bits in the same word. `Dh` is **reserved** in BNN: this vaeg build exposes a second backing window there and it was checked separately, but don't ship code that assumes `Dh` is portable or that both windows are needed on every model.

Keep code, stack and copy buffer in conventional RAM. For each bounded read: save flags, `CLI`, read and save the map word, select the window, read a short chunk, restore the entire map word, then restore flags. Do not call DOS or a BIOS service while the dictionary is mapped. Decode outside the critical section; cut reads at 64 KiB segment boundaries and re-enable maskable IRQs between chunks when the caller had them enabled. This is the same save/restore pattern VAIO uses for TVRAM. `CLI` doesn't protect against NMI or a bus master; this test doesn't qualify those cases.

**Gate:** eight cold 2HD boots: vaeg VA and VA2 × 256 and 640 KiB × JFP master-disabled and enabled for the conversion phase. The banking phase ran **before** JFP initialization on every boot, with the DOS text BIOS already in use. The probe alternated caller IF on/off across 128-byte reads and checked IF and the restored word after each read. For both selectors, both checksum accumulators for each of the four segments matched the corresponding local image slice on both models. Full TVRAM payloads matched immediately before/after banking. The guest printed no dictionary bytes or candidates; checksum values were read from guest RAM and compared only in scratch. The probe received an emulated key tap after conversion, then the COM returned to DOS and a new `ECHO` command produced its expected output. This checks ordinary keyboard and text operation after restoration, not concurrent firmware access with the wrong map installed.

## 2. Direct reader: promising, not yet validated

A separate private trace recorded dictionary-window accesses for three short readings on each model. First conversion repeatedly touched reading-dependent regions and then regions associated with the candidates; candidate cycling on VA2 usually revisited a small candidate region, including a repeat visit when stepping back. The same VA cycles showed no reads of the two dictionary windows in this sample. This is evidence of an indexed lookup and ordered alternatives, not evidence that the models use the same index, that all candidates are read directly from that window, or that BIOS order is on-ROM order. Checks for verbatim candidate strings in several common encodings at the traced reads did not explain the candidate records.

No independent reading-to-candidate lookup or dictionary ordering was demonstrated. An adapter looks feasible, but the model dispatch, reading index, candidate decoding, ties and fallback rules still need work. Estimate **one to two engineer-weeks** for a small two-model exact-reading proof of concept and private comparison corpus, assuming the remaining encoding can be resolved. Robust bounds and revision checks, segmentation and order parity are separate work. Do not make a parser the critical path of kana input.

## 3. Documented BIOS as a conversion engine

**Yes, for the tested foreground path.** From a plain DOS prompt, call `ResJFP` once outside DOS, flush the keyboard startup queue, and use `SetJFP` to leave the ROM front end **master-disabled**. Use the primitive keyboard functions (`603KEYB`, `PrmSnsK`/`PrmGetK`), not the main JFP-aware path. Pass the project's NUL-terminated, full-width Shift-JIS reading at `DS:SI` and an owned output buffer at `DS:DI` to `Sug1st`, then `SugNxt`/`SugPrv` (`618JFP` §6.18.3). Keep the same reading during a candidate session and serialize sessions: this is a stateful BIOS, not a stateless lookup API. Copy validated results into project-owned buffers and commit them there, without invoking `Decide` or its learning path. The test used a guarded 128-byte output buffer for short inputs; it did not establish a production buffer bound. Verify the phrase metadata before using it: for these fixtures the two AX byte roles appeared reversed relative to the local manual transcription.

On all eight boots, for each of three readings, first/next/next returned three distinct terminated candidates and previous returned the prior candidate. Enabling JFP for the control gave the same results as leaving it master-disabled on the same model. The models did not always start with the same candidate or segment a reading the same way. The TVRAM payload (including the label row) matched before/after the conversion sequence; it did not need a BIOS composition UI. A separate primitive read received the injected key. The probe did not implement a composition painter or deliver candidates to CON. These measurements isolate the conversion backend from input/rendering; they do not exercise a complete FEP.

During conversion the temporary hooks counted **zero INT 21h and zero INT 83h entries**. Setup, separately, observed **two DOS open calls**, consistent with `ResJFP` attempting to load the default files (not supplied on this disk). The hooks measure interrupt entries, not arbitrary internal calls or all RAM writes. Keep initialization/reset out of device requests. Until a nested-call contract is proven, keep conversion itself outside DOS/device/IRQ context too. J3b.3 must choose an explicit foreground owner or design and qualify a deferral mechanism; an InDOS check that merely suppresses conversion would not make it work at the DOS prompt.

## 4. Size and latency

| Backend | Incremental resident budget (estimate, either RAM size) | Conversion latency |
|---|---|---|
| Project input/UI + BIOS glue | **3–6 KiB**, including composition, candidate and delivery buffers. Relies on firmware work areas remaining reserved; this is not a proposal to reclaim them. | In vaeg, short `Sug1st` calls ranged from **68–463 ms on VA**, **73–86 ms on VA2**. Next/previous took about **0.9–1.4 ms on VA**, **36–38 ms on VA2**. |
| Project input/UI + direct reader | **4–10 KiB**, assuming bounded work buffers and an on-ROM index, not a full RAM copy or a resident expanded index. | **Unmeasured.** A provisional target is **5–30 ms** for an indexed short reading: at the probe's scan cost, touching 256–1024 bytes alone costs roughly 1.5–6 ms, before search/decoding/UI. Neither the bytes touched by a future reader nor this target is established. A linear scan is not a per-keystroke design. |

BIOS times bracket the calls in vaeg guest machine clocks (nominal 7.9872 MHz accounting), including interrupts and probe marker overhead, not wall clock and not hardware benchmarks. They pool both RAM sizes and BIOS modes; corresponding samples were similar at 256 and 640 KiB. They exclude initialization and the future UI. The slow VA first conversion is a reason to measure a larger corpus, not to promise interactive latency from a three-reading test. The two size budgets are about 1–2.4% and 1.6–3.9% of **installed** RAM at 256 KiB, about 0.5–1% and 0.6–1.6% at 640 KiB. The cost as a share of available DOS RAM is higher. No resident driver was built or measured.

## Recommendation and limits

- **J3b.2:** implement project-owned romaji/kana, composition UI and primitive key arbitration independently of the dictionary. Gate both label layouts and DOS status/peek/flush, editing, break and Shift-JIS byte order. Define a backend interface for begin/next/previous/cancel; keep the existing J3a path selectable and unchanged.
- **J3b.3:** prototype the documented BIOS backend first, with foreground initialization and conversion. Gate bounded buffers and latency, both models/RAM sizes, misses and candidate limits, no ROM UI, and a DOS-safe caller design before wiring it into CON. If it requires unsafe DOS nesting, conflicts with reclaiming ROM work RAM, or has unacceptable coverage/latency, use the private direct-reader investigation as the fallback. The [FreeDOS M20 decision](https://github.com/FreeDOS-88VA/freedos/blob/7f467a2/docs/porting/m20-report.md#decisions-carried-to-m21-japanese-support) plans to replace the ROM FEP and reclaim its RAM; reusing its engine doesn't satisfy that reclamation goal by itself.
- **NOT RUN:** real hardware, VA3, other ROM revisions/media (including 2D), NMI/DMA and interrupt-stress controls, mapping from a GVRAM/kanji-ROM client, reset-free conversion (see the older [J3.0 probe](J3.0-jfp-probe.md) for its separate negative controls), successful external dictionary or gaiji loading, learning, nested DOS/CON or IRQ conversion, long/invalid inputs, candidate exhaustion, interleaved sessions, full FEP UI, independent direct decoding/ordering, and hardware timing. An instruction-trace attempt did not run: the stock emulator build lacked that facility. Dictionary-window read tracing did run separately.

## Evidence and reproduction

The matrix reused the [J3a](J3a-rom-jfp-input.md) 2HD release-test image built at `e240386d` (no product-source difference from J3b.1 base `6e0b446`). It used vaeg `Rel.20261121 (m152, a913388f)`, an explicit RAM capacity with auto-sync, and no saved backup memory. The probe checked the DOS PSP allocation ceiling for each configured capacity. No new build of DOS was run. The two read traces were separate, 640 KiB master-disabled boots with just the conversion half of the probe instrumented; their timings are not used here.

Private files under `../pc88va/tmp/j3b/` (outside every Git tree): `NOTES.md`, `J3BPROBE.NAS`, `run.py`, `check.py`, `gate.checked.txt`, `trace.gdb`, `structure.py`, `structure.txt`. Supporting private captures are in `gate/`, `dict-trace-va/` and `dict-trace-va2/`. `NOTES.md` gives the rerun commands. No test programs, checksums, captured screens, dictionary contents or firmware-internal addresses are published with this milestone.
