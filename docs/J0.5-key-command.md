# J0.5 — KEY and INT DCh programmable keys

**Gate: VA 39/40, VA2 39/40** on vaeg PR [#82](https://github.com/nakatamaho/vaeg/pull/82), `Rel.20261121 (m153, 6367e5d3)`. The unchecked item is the live PC-98 **shifted label** comparison, not VA input or label updates. Pre-install vector checks passed on both models. CHKDSK free conventional memory fell **288 bytes** on each. See the [checked observations](J0.5/observations.txt).

## NEC MS-DOS 3.3D observations

Booted system disk 1 in NP2kai SDL2 (`5939e0c6`) and ran [`DCKEYS.COM`](../tests/pc88va/DCKEYS.NAS) at COMMAND. The default read used an 800-byte buffer prefilled with `CCh`; the probe recorded returned AX, FLAGS and the entire buffer. A nonzero CH (`55h`) worked, i.e. the services select on **CL**. `DS:DX` is the buffer for both directions. These are fixed-width records, not ASCIIZ records concatenated without padding:

| AX | NEC result for CL=0Ch | VA result |
|---|---|---|
| `0000h` | 386 bytes: 10 F, 10 Shift+F, then 11 editing keys. No separate 320-byte F-only bulk selector found. | Byte-identical, including padding. |
| `0001h–000Ah`, `000Bh–0014h` | One 16-byte slot, F1–F10 and Shift+F1–F10 respectively. | Same. |
| `0015h–001Fh` | One 6-byte slot, in the editing-key order given in [J0.3](J0.3-fkeys-input.md#table-and-sources). | Same; VA uses its existing physical mappings. |
| `0020h–0039h` | Extended selectors (VF, Shift+VF, Ctrl+F, Ctrl+VF, Ctrl+XFER/NFER); sampled `20h`, `2Ah`, `39h` each returned 16 zero bytes on this keyboard/default setup. | 16 zero bytes; no storage or input mapping for these selectors. |
| `003Ah` | 176 bytes: Ctrl+XFER/NFER and Ctrl+F1–F10, all zero on the test setup. | Same read; writes ignored. |
| `003Bh` | Buffer untouched. | Same. |
| `00FFh` | 786 bytes: F (160), VF (80), Shift+F (160), Shift+VF (80), editing (66), Ctrl+F/Ctrl+VF (240). | Byte-identical at boot. The extended ranges are zero-filled on reads and skipped on writes. |
| `0100h` | Separate data-key service: 514 zero bytes on the reference setup. | Not implemented; buffer untouched. |

The individual selector ranges and the ordering of the all-zero extended groups were cross-checked with FreeDOS(98) [`int29dc.c`](https://github.com/lpproj/fdkernel/blob/c9ce245e0447003645adce47bd34960ae276d4bd/nec98/kernel/int29dc.c#L818-L867) and [`conkey60.asm`](https://github.com/lpproj/fdkernel/blob/c9ce245e0447003645adce47bd34960ae276d4bd/nec98/kernel/conkey60.asm). No GPL implementation code was copied. Not every individual selector was called; the byte-for-byte bulk comparison does cover their default table positions.

- **CL=0Dh:** Writing a 20-byte source `ABCDEFGHIJKLMNOPQRST` to F1 left `ABCDEFGHIJKLMNO` + NUL in its 16-byte slot. F2, the rest of the compact table and the read guard were unchanged. Writes of `FEh` + five label bytes + `f-one`/`s-one` came back with the prefixes intact. The key delivered just its payload; the normal label changed to `NEW`. Shift+F1 delivered `s-one` but this NP2kai/DOS configuration did not display the shifted line while Shift was held, even when the key was tapped ([NEC capture](J0.5/nec-clean-sf1.png)). VA/VA2 display the `SHIFT` label while Shift is down.
- **Return:** Sampled reads and writes returned AX unchanged, including the invalid `003Bh` case. Carry was set on entry and stayed set; there was no error or length returned in AX. An unknown `CL=FFh`, `AX=1234h` returned to the caller with AX and buffer unchanged and the same low FLAGS as VA. Only low FLAGS were compared; high reserved bits read differently on the two CPUs. Other unknown CL values were not individually tested.
- **`date` and `time` CR:** Because live Shift did not expose the NEC shifted line, `DCKEYS L` copied the **unlabelled Shift+F9/F10 definitions** to normal F9/F10 on each platform using the same API. NEC shows a small **CR** glyph after each ([NEC](J0.5/nec-clean-cr.png)); VA also shows a glyph, in its own ROM font ([VA2 crop](J0.5/va2-cr-label.png)). Neither renderer treats the embedded CR as a newline; the glyphs differ. The J0.4 VA rendering was left unchanged. Direct inspection of the shifted line itself on NEC: **NOT RUN** (not exposed by held Shift).

### NEC KEY.EXE (system disk 2)

`KEY /?` identifies version 3.20 and shows `KEY [[drive:]file][/S|/N] | /?` ([help](J0.5/nec-help-final.png)). The *MS-DOS 3.3D User's Guide*, printed p. 188 (PDF p. 202), says `/S` and `/N` enable and disable **Ctrl+F-key functions**; they are not save/load switches. `KEY TEST.KEY`, `KEY TEST.KEY /S` and `KEY TEST.KEY /N` each reported file not found with a missing file.

Bare `KEY` opens a full-screen [menu](J0.5/nec-menu-again.png) navigated with Up/Down and Return. Its choices are edit key file, edit live key table, register key file, display key file, display live key table, options and exit. Display/update are grouped by ordinary, Shift and Ctrl function keys, cursor/editing keys, and data keys. The Shift edit screen lists 15 entries and spells control bytes such as `<CR>` separately from printable text. In **edit live table → Shift+F → F01** I entered `xyz`, selected the end entry on the key list and category screens, then exited KEY; physical Shift+F1 typed `xyz` at the prompt ([edit](J0.5/nec-menu-key-end.png), [result](J0.5/nec-key-applied.png)). Escaping out of the edit screens instead did not apply my changes.

The **edit key file** path asks for an existing input file, a destination (default `\KEY.TBL`), and confirmation. Missing input was rejected; feeding `NUL` gave [invalid format](J0.5/nec-nul-final.png). **Register key file** asks for the input file to load, also defaulting to [`\KEY.TBL`](J0.5/nec-register.png). I did not find a usable example on the tested system disks. Successful NEC file save/load, the NEC on-disk format, and applying `/S`/`/N` to a valid file: **NOT RUN**. The VA file below is not presented as compatible with `KEY.TBL`.

## Vector and implementation

- The PC-88VA BNN Technical Manual §2.1 (printed p. 17) lists `C0h–FFh` as **Free**, so DCh is not an assigned ROM service. On VA **and** VA2, the [scratch boot sector](../tests/pc88va/DCBOOT.NAS) read the IVT before loading DOS: AL=`03h` means DCh matches DBh and DDh and points directly to an `IRET`. On the unmodified J0.4 MS-DOS build, `DCKEYS V` saw the same two properties after boot. No ROM-internal addresses are reported. This checks both ROM startup and the baseline DOS, not the behavior of arbitrary installed TSRs.
- VAIO installs DCh in `RE_INIT`, with IRQs masked across the vector update. The handler leaves registers and return flags unchanged. Writes transfer at most 15 or 5 bytes per slot, force the last byte to NUL, discard any remaining expanded CON key string, and send each affected slot to ROM `DefSft`. ROM expansion stays off. When the label line is hidden, a write leaves 25 main rows in place; showing the line reveals the new definition. No B1 stack-switch code changed.
- [`KEY.COM`](../pc88va/VAKEY.ASM) runs nonresident and calls only DOS and DCh. `KEY` lists all 31 definitions to stdout; control and high bytes are escaped, so a listing cannot execute embedded CON escapes. Set a named key with `KEY SF1 dir b:\r`, or e.g. `KEY F10 \xFELABEL\eZ` for explicit label `LABEL` and payload `ESC Z`. `\r`, `\e`, `\xHH` (nonzero byte), and `\\` are supported. Names are case-insensitive; the definition is not. CLI definitions longer than the payload capacity (15 or 5 bytes **including** any label prefix) are rejected, whereas DCh itself truncates. Bare `KEY` and single-key setting are VA's plain-command alternatives to NEC's menu.
- `KEY /SAVE MY.KEY` saves all definitions. `KEY MY.KEY` loads them, following NEC's positional filename form; `KEY /?` shows help. The VA binary file is exactly 392 bytes: ASCII `VAKEY`, version byte `01h`, then the 386-byte compact table. The command checks size and magic before modifying any key. It does not prompt before overwriting on `/SAVE`. No full-screen menu, NEC file format, `/S` or `/N`, VF/Ctrl/data-key programming, or explicit CLI clear operation (a file can store empty slots).
