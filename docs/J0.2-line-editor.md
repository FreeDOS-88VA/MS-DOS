# J0.2 — NEC line-editor keys

**VA2 gate remains blocked at step 5.** Steps 1–4 and 6–8 passed, and ESC Z inserted `^Z` at the COMMAND prompt. `COPY CON` stalled before EOF on both the IBM-editor baseline and the J0.2 build. In stalled debugger runs the guest stopped reaching VAIO's normal CON keyboard poll. Why it stopped is unknown; no product code changed in the recheck. The non-PC88VA kernel comparison passed.

## Key choices

The distribution kernel uses `v4.0/src/DOS/MSSW.ASM` (included by `INC/MSDOSME.ASM` and `DOS/MSCTRLC.ASM`), not `STDSW.ASM` or `HIGHSW.ASM`. The PC88VA branch sets `ESCCH=1Bh` and `DOSMES.ASM` selects the existing ESC-letter table. `IBM` is unchanged; no build, VAIO or COMMAND source needed to change.

NEC's *PC-9800シリーズ MS-DOS3.3D ユーザーズガイド*, Appendix D.7, printed p. 205 (PDF page 219), documents **Ctrl-X** to cancel the line without altering the template and **Ctrl-P** to toggle printer echo, with **Ctrl-N** doing the same. Thus PC88VA uses `CANCEL=18h` and `TOGLPRN=FALSE`: despite the old switch comment about separate on/off keys, `CTRLC.ASM` makes `PRINTON` and `PRINTOFF` labels for the same toggle, and the false setting enables the Ctrl-N alias. D.8 on that page lists the template functions. The PDF was extracted and checked in scratch only. Runtime printer echo was **NOT RUN**.

## Step 5 investigation

- **IBM baseline:** [`eof-ibm.input`](J0.2/eof-ibm.input) used the original input schedule with `@key ctrl-z` instead of ESC Z. The baseline stopped at [`F` at frame 1400](J0.2/eof-ibm-1400.png), not exactly `FIRST`, and still showed only [`F` at frame 2300](J0.2/eof-ibm-2300.png), with no returned prompt or `TYPE` output. The image was unchanged and `readfile.py` returned `not found: T.TXT`. The failure therefore predates the NEC editor change.
- **Paced J0.2:** [`eof-slow.input`](J0.2/eof-slow.input) waits an extra 300 frames after the command and sends each body character separately with `@wait 10` (the parser strips trailing spaces, so each body space is sent with the following `L`). [Captures every 100 frames from 700 to 4800](J0.2/eof-slow-frames.png), the [final screen](J0.2/eof-slow-4800.png) and the [decoded final TVRAM](J0.2/eof-slow-tvram.txt) show no body text. Three more cold boots stopped with no body text, [`FIRS`](J0.2/eof-slow-partial-5000.png), and no body text, respectively. The scheduler reached the `TYPE` command in all four runs, but the guest did not return to a prompt. Slow X11 key events (100 ms down/up intervals after a five-second wait after `COPY CON`) [also stalled](J0.2/eof-x11-end.png), as did a [paced run](J0.2/eof-m152-5000.png) with vaeg m152 `6c40ac5d`. The disk was unchanged and `readfile.py` could not extract `T.TXT` in any of these runs. See [run and disk-check results](J0.2/recheck-observations.txt).
- **Guest polling check:** [`copy-poll.debug`](J0.2/copy-poll.debug) uses vaeg `--debug-script` in place of the headless input script (use an existing empty `--debug-output-dir`). `1000:03FC` is `CISTAT` in both builds' VAIO, verified against the assembled bytes; this is DOS driver code, not a ROM address. The breakpoint fired at the prompt in both builds. After entering `COPY CON` and **sending no body input**, the baseline missed the breakpoint throughout frames 1400–2200 on two runs; J0.2 hit it. In a [variant with `FIRST LINE` sent at 1050](J0.2/copy-poll-first.debug), J0.2 missed the late breakpoint and IBM hit it. The [debug events](J0.2/recheck-observations.txt) show that the stall is intermittent and that, in stalled runs, the guest stops reaching the normal CON keyboard poll. In particular, a burst of body text is not required to trigger it. The failing guest routine and underlying cause were not identified.

### What vaeg queues

References are to vaeg `5c2307ac`. [`sdl2/headless_input.c:38–43,311–312,369–398,465–550`](https://github.com/nakatamaho/vaeg/blob/5c2307ac/sdl2/headless_input.c#L465) limits the script to 256 commands, starts at guest frame 600, waits 120 frames between ordinary commands and also waits for active paste to finish. `@text` starts a paste without adding Return. `@key` phases are three guest frames apart (modifier make, key make, key break, modifier break for a chord). The `injected` message reports the **start of a paste**, not receipt by DOS.

[`sdl2/kbdpaste.c:33–42,334–371,400–504`](https://github.com/nakatamaho/vaeg/blob/5c2307ac/sdl2/kbdpaste.c#L400) allocates actions for the text and sends make/break separately at a minimum of 20 host ms **and** two guest frames between phases in VA2 V3 mode. Shifted characters add two modifier transitions. [`sdl2/kbdinject.c:29–39`](https://github.com/nakatamaho/vaeg/blob/5c2307ac/sdl2/kbdinject.c#L29) feeds the guest key path. The emulator's serial keyboard FIFO is **128 scan bytes** ([`io/serial.h:2–7`](https://github.com/nakatamaho/vaeg/blob/5c2307ac/io/serial.h#L2)); [`io/serial.c:434–452`](https://github.com/nakatamaho/vaeg/blob/5c2307ac/io/serial.c#L434) sets overrun if a make/break arrives when it is full.

That FIFO is distinct from the guest ROM primitive queue, which VAIO senses and drains through INT 82h `0Ah/09h` ([`v4.0/pc88va/VAIO.ASM:341–377`](../v4.0/pc88va/VAIO.ASM#L341)); VAIO caches at most one byte itself. NEC's `603KEYB.TXT` §6.3.5 documents a finite 32-byte keyboard queue buffer. If DOS does not drain it fast enough, accumulated input can exceed its capacity; paste has no backpressure from that buffer. ROM queue occupancy and exact drop behavior were **NOT RUN**. Overflow is not necessary to explain the observed stall: the baseline can stop polling without any body input and pacing does not make the gate pass.

## Non-PC88VA comparison

Fresh scratch builds from `release/msdos-va` (`f8cd7e8`) and `3d5da84` used the same builder and tools. In scratch only, set `DEFINES = ()`, remove `-DPC88VA` from bootstrap COMMAND's MASM invocation, and return after `nmake('DOS')` (before BIOS/image work). Both builds completed; the `msdosme.asm` and `msctrlc.asm` commands had no `-DPC88VA`. `cmp` found the two 37,376-byte `tree/v4.0/src/DOS/msdos.sys` files byte-identical (SHA-256 `573626782a3c45f0d9e5f00af1bd0f52a7de44bea96d2a2d3d660e9ae06158d5`).
